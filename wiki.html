Overview

Lilly AI runs on your Android phone via Termux with a Docker backend. It has:

  • 9 avatar agents — each with distinct personality and strengths
  • 23 phone sensors — light, accelerometer, gyroscope, GPS, battery, etc.
  • Natural language automation — "when X happens, do Y"
  • Notification intelligence — reads and prioritizes Android notifications
  • Voice interaction — speak to Lilly, she speaks back
  • Camera vision — YOLOv8 object detection from phone camera or browser webcam
  • Face recognition + keypoints — SCRFD + ArcFace + FAISS identifies people; overlay draws eyes/nose/mouth dots
  • Unknown-face OSINT — opt-in reverse-face lookup unveils names + social accounts for unrecognized people
  • Community skills — 90k+ OpenHuman skills; "explain anything" makes interactive HTML explainers
  • Self-training AI — YOLO automatically improves by collecting data and fine-tuning
  • Picture-in-Picture — YouTube while chatting

📷 Camera & Vision (YOLO)

Lilly can see through your phone camera, browser webcam, and Blink home security cameras — all at once in the Camera Window.

How It Works

Camera frames are sent to the backend every 2-3 seconds. YOLOv8 detects 80+ object classes (person, laptop, phone, cup, chair, car, etc.) and returns bounding boxes + labels.

Camera Window

Click the 📷 camera button in the toolbar to open the Camera Window — a 3-panel view showing:

  • Blink Cameras (left) — cycles through your Blink security cameras every 8 seconds
  • Phone Camera (center) — live feed from your Android phone via Termux sensor server
  • Webcam (right) — your browser's webcam feed

The Camera Window is draggable — grab the header bar to move it. All three feeds run simultaneously with YOLO detection in the background.

🧠 YOLO Self-Training Agent

Lilly can automatically improve its vision by collecting training data and fine-tuning the YOLO model.

How It Works

The self-training agent monitors all YOLO detections, collects training samples, and fine-tunes the model to improve accuracy over time.

Features

  • Real-time monitoring — tracks detection confidence, accuracy, and class distribution
  • Auto-collection — saves training samples when confidence is in the "uncertain" range
  • User feedback — correct misclassifications to improve future training
  • Auto-training — fine-tunes YOLO when enough samples are collected
  • Model evaluation — tests new models before deployment
  • Auto-deploy — deploys improved models automatically

Training Data Collection

When YOLO detects an object with confidence between 30% and 70%, the agent automatically saves the image and bounding box as a training sample. This "uncertain" range is where the model needs the most improvement.

Self-Training Process

  1. Monitor — Track all detections in real-time
  2. Collect — Save training samples (images + labels)
  3. Correct — Users fix misclassifications via API
  4. Train — Fine-tune YOLO on collected data
  5. Evaluate — Test model performance (mAP, precision, recall)
  6. Deploy — Deploy improved model if better than current

😀 Face Recognition & Keypoints

Every “person” detection (oiv7 labels Man, Woman, Human face, person…) gets a face scan: Lilly finds the largest face inside the box, embeds it, and — if the face is enrolled — stamps the box with the person’s name. It also publishes 5 face keypoints (👀 left/right eye, 👃 nose, 👄 mouth corners) so the overlay can draw them instantly.

How It Works

  1. SCRFD (det_2.5g.onnx) detects faces + keypoints in the frame
  2. ArcFace (w600k_mbf.onnx) embeds the largest face in each person box → 512-dim vector
  3. FAISS index looks up the nearest enrolled name above the match threshold
  4. Detection is enriched with name (if matched), kps (5 keypoints), and face confidence

Keypoint Overlay

Vision responses carry kps: an array of 5 normalized [x, y] points. The Android overlay draws them as glow-dots inside each person box — cyan eyes, magenta nose, orange mouth corners — with a dark outline to stay visible. Keypoints persist for 2 seconds between face-scans, so the dots render on every frame without waiting (instant overlay).

Enrollment

Enroll a face once, and Lilly remembers it forever (512-dim vectors persisted to known_faces.json):

curl -X POST http://localhost:8098/api/faces/enroll \
  -H "Content-Type: application/json" \
  -d '{"name":"Alice","image_b64":"<base64 JPEG>"}'

Say "remember this face as Alice", or manage via GET /api/faces / DELETE /api/faces/{name}.

🕵️ Unknown-Face OSINT (Opt-in)

Tier 2 of face recognition: when a face is not enrolled, Lilly can try to figure out who it is via public reverse-image search — and surface social-media accounts.

How It Works

  1. Vision server samples an unsolved person’s face every 8s (max 12 buffered)
  2. It pushes the face crop to Lilly: POST /api/vision/faces/osint_unknown
  3. Lilly runs Yandex reverse-face search (default provider) → candidate name (conf ≥ 0.35)
  4. Lilly fans the name out to its OSINT stack (osint_agents + scrapling) → social accounts (Facebook, Instagram, LinkedIn, X, TikTok, GitHub, VK, OK, Bluesky…)
  5. Lilly pushes the result back to POST /api/vision/face/identify; the box is re-stamped with the matched name + social_accounts

Enable It (off by default)

Set in your .env / docker-compose:

FACE_OSINT_ENABLED=1                # turn the tier on
FACE_OSINT_PROVIDER=yandex          # yandex (default) or test
FACE_OSINT_COOLDOWN=60              # min seconds between lookups per face
OSINT_PUSH_URL=http://127.0.0.1:8098/api/vision/faces/osint_unknown

Endpoints

EndpointMethodPurpose
/api/vision/faces/osint_unknownPOSTVision → Lilly: queue an unknown face for OSINT
/api/vision/face/identifyPOSTLilly → Vision: re-stamp a box with identity + accounts

⚠️ Reverse-image search results are best-effort and brittle — treat as leads, not verdicts. The tier is fully opt-in and never blocks the live vision loop.

📡 Bluetooth Broadcast (Earbuds Mode)

Your Pixel 10 can advertise itself as a Bluetooth LE device — like earbuds in pairing mode. When nearby, it will appear in Bluetooth scans with your chosen avatar name and image.

How It Works

  1. Open the Lilly web UI on your host machine
  2. Click the hamburger menu ☰ → Broadcast button
  3. Choose an avatar image (🐶 Puppy, 🦊 Fox, 🐱 Cat, etc.)
  4. Set a device name (e.g., "Lilly Pup")
  5. Click "Start Broadcast" — your phone now appears in Bluetooth scans

Nearby phones will see your device appear as a discoverable BLE peripheral. They can open the broadcast web URL to see your avatar image — just like earbuds showing a pairing prompt.

Permissions Required (Android 12+)

On your Pixel 10, grant these permissions to Termux:

  • Location — Allow all the time (required for BLE advertising)
  • Nearby devices — Allow (Android 12+ Bluetooth permission)
  • Bluetooth — Allow

Also enable Location services: Settings → Location → High accuracy

📡 Container-Side Broadcast (No Phone Required)

Starting a broadcast directly from the Docker container — no phone needed. Uses ble_advertiser_host.py which talks to the host Bluetooth adapter via raw HCI commands (hcitool/hciconfig). This is the container equivalent of the Bluetooth LE Spam APK, using your own payloads (name, service UUID, image URL) — no third-party fake-device payloads.

  1. Ensure the host machine has a Bluetooth adapter and BlueZ is installed
  2. The container (via start.sh) auto-starts ble_advertiser_host.py on port 8110
  3. Broadcast from the API: 
    curl -X POST http://localhost:8098/api/bluetooth/advertise \
  -H "Content-Type: application/json" \
  -d '{"name":"Lilly Pup","mode":"balanced","image":"/static/lilly/puppy-avatar.svg"}'
  4. Check status: curl http://localhost:8098/api/bluetooth/advertise/status
  5. Stop broadcast: curl -X POST http://localhost:8098/api/bluetooth/advertise/stop
  6. Scan for nearby BLE devices: curl http://localhost:8098/api/bluetooth/advertise/scan
  7. Or just say: “broadcast” / “advertise” / “beacon”
ModeDescription
bleBLE advertising only (silent radar presence)
classicClassic BR/EDR headphone-pairing popup on nearby phones
fast_pairGoogle Fast Pair BLE — Android bottom-sheet popup
both / balancedClassic + Fast Pair BLE simultaneously (default, best coverage)

ℹ The container advertiser is tried first by _bt_proxy (always-local, no phone dependency). If no Bluetooth adapter is available, the phone-side advertiser (sensor server :8099 or standalone :8100) is used as a fallback. Download ble_advertiser_host.py to run standalone.
